## 确认的问题

1. Artificial Analysis 表中的外部 Logo 被阻断时，原生失败图片的基线/占位导致异常行高。1440px Chromium 基线中第一数据行为约 152px，而图片的 CSS 尺寸很小。不能仅检查 img 的 bounding box 就认定单元格正常。
2. 所有内容统一限制在 820px。即使工作区很宽，数据表也无法利用空间；旧列宽预算只有几个长度档位，数字列与正文列按比例一起扩大。
3. 表格布局读取 KaTeX 转换后的 HAST，直接拼接节点文本会重复读取 MathML、TeX 注释和视觉输出。公式长度不能这样计算。
4. 工作区的通用 button/font/focus 规则，与 Markdown 工具栏拥有同等或更高优先级。局部控件可能被全局 shell 外观覆盖。
5. 手写模型来源表未使用 Markdown 表格组件，存在两套滚动、主题、表格边框规则。

## 处理方式

保留 React Markdown + remark-gfm + remark-math + rehype-katex + Mermaid。它们已经负责标准语法、公式、图表和安全输出。本轮不是解析器缺能力，不引入第二套 Markdown 解析器，也不把所有普通知识表升级成可编辑 Data Grid。

- `MarkdownImage`：Logo 使用独立、固定尺寸的 inline-flex 框，加载失败时显示紧凑文字占位；普通图片保留独立的失败提示。品牌名字仍然可读，图片不是信息的唯一载体。
- `table-layout.ts`：以可见文本、中文/英文宽度预算、数字和日期的显示需求分配列宽。KaTeX 只取一份注释。算法只影响排版，不改变数值、单位、列顺序或模型身份。
- `MarkdownTable`：基于真实滚动容器和表格字号重新计算，监听侧栏变化、字体加载和窗口尺寸。先保障最低可读宽度，再分配舒适宽度，额外空间优先给文字列。一/两列优先适应容器；更宽表格只在组件内滚动。SSR 初始输出与无 ResizeObserver 降级仍保留。
- 数据派生页面设置 `readingLayout: reference`，可用最大宽度 1280px。段落、标题等仍限制在 820px；短两列表格不无限拉宽。普通原理文章保持 820px 阅读宽度。没有使用 100vw 或把侧栏宽度额外加到页面上。
- 模型来源表也使用 `MarkdownTable`，共享对齐、行底色、主题与键盘横滑规则。保留 HTML table/th 的语义，不引入原生 select/details UI。
- 降低工作区通用按钮与焦点规则的选择器优先级，局部 Markdown 控件负责自己的外观。滚动条、文本选择和失败占位跟随局部明暗主题；没有恢复阴影。

## 验证与复现

`scripts/audit-markdown-layout.mjs` 在本地开发服务器运行时读取全部公开页面，输出 DOM 数量、列宽、行高和截图。该审计主动阻断外部资源，结果不是线上网络可用率。

新增 `workspace-markdown.spec.ts`：28 页面 × 390/1440/1920px × 明暗主题，共 168 个页面配置；每个配置检查各表列宽合计、页面及阅读容器的溢出。另测 320/768/1024/1440/2560px 下实时侧栏变化、关联资料、根字号16/20px、横向滚动控制与主题切换。生产配置也包含此文件。

新增 `markdown-layout.spec.ts` 与 `tables.md`：测试一至七列、对齐、长 URL/代码、含公式单元格、图片成功/失败、任务列表、脚注及与全局不同的局部主题。检查 Logo 图框和所在行高，不只检查图像元素尺寸。

使用 `npm run build`、`npm run test:browser`、`npm run test:production` 验证。构建保留原 Markdown 实际渲染、数据图谱和 Python 教学代码测试。浏览器验收使用 Chromium，不据此声称已完成真实 iOS Safari 或所有浏览器验收。来源、榜单、报价与核验日期均未改变；布局回归通过不代表内容已重新核验。
