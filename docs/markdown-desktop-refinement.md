# 大屏 Markdown：对齐、内容宽度与主题规则

## 为什么不替换 Markdown 解析库

现有 `react-markdown` + `remark-gfm` 负责 CommonMark/GFM 解析，`remark-math` + `rehype-katex` 负责数学，Mermaid 负责围栏图表。React 组件负责呈现，CSS 和表格布局负责宽度。此次问题来自呈现层，不是缺少第三方解析库。继续保留安全的 URL 处理和原生文档语义，不引入 MDX、HTML 字符串注入、另一套解析器或重型数据网格。

官方依据：
- https://github.com/remarkjs/react-markdown#appendix-b-components
- https://github.com/remarkjs/remark-gfm
- https://www.w3.org/TR/css-tables-3/

## 已定位的问题

旧参考页将标题、段落和小表各自居中到 820px，却让其他表格铺满 1280px。1920px 视口下，左边缘会相差约 230px（外框；内表另有 1px 边框偏移），目录面板改变宽度后差值还会变化。这是 CSS 布局问题，不是 Markdown 语法错误。

旧列宽分配还要求所有表格填满可用区域，剩余空间分给每一个文字列。短供应商名称、状态和长说明被视为相同的可伸展内容，宽屏下产生不必要的空白。

实测截图又发现短数字列的“输入/输出”表头换成了两行：按字符预算得到的 4em 列宽，还要扣掉左右各 1em 内边距、边框和取整，实际不足两个完整汉字。列宽预算新增了边框与取整余量，并以真实文本行数进行回归检查；没有给所有长表头强制 nowrap。

## 新规则

- 参考页保持至多 1280px 的工作区，但标题、说明、正文、窄表和宽表共用一条左对齐线；普通文章仍保持居中的 820px 阅读列。
- 表格框宽度上限为 `min(父容器宽度, max(820px 对应 rem, 内容首选宽度预算))`，不为使用宽屏而硬拉宽小表。
- 表格框与实际表格使用相同字号，内容预算以同一 em 单位计算；字体加载、根字号、侧栏及面板变化都会触发宽度更新。
- 空间不足先从首选宽度缩到可读最小宽度，再仅在表格内部横滑；1–2 列继续在小屏换行。
- 到达首选宽度后，优先把额外空间给长说明，而不是短类型/状态字段。
- 手写 MD 的左/中/右对齐原样保留。JSON 派生表仅把原始值类型为有限 number 的列生成右对齐，不解析字符串金额，不改写数字、排序、来源与核验日期。
- 明暗、局部主题滚动条、无阴影、加载失败 Logo、键盘焦点和强制色彩模式沿用或补齐统一规则。

## 验证

`workspace-table-typography.spec.ts` 检查 1280/1440/1920/2560/3840px、明暗主题、对齐线、宽度预算、数字列、双侧面板变化、20px 根字号、390px 横滑和回到大屏后的滚动控件恢复，并对全部公开文档统计表格、行、普通代码块、图表容器、显示公式、列表和引用。

`workspace-table-labels.spec.ts` 使用浏览器实际文本行数验证大屏数字短表头不会意外竖排。既有 `workspace-markdown.spec.ts` 继续检查全部文档的局部与整页溢出、两种主题和侧栏变化。Mermaid 绘出真实 SVG 由原图表测试单独验证，不将容器数量当成绘图通过。测试编写的数量不是测试通过的声明，以对应提交 CI 为准。

不新增运行时依赖，不更换知识工作区，不调整源研究数据。Chromium 自动化不等于真实 Safari/iPhone 验收。
